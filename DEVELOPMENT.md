# Project context - dhis2-app-skeleton

This file is the project OVERVIEW and CONVENTIONS, written for the people who work on the project; AI agents read it too, as the source of the project's facts. How the AI protocol applies to the project lives in [`.est_ai/project.md`](./.est_ai/project.md). It is distinct from the behavioral capability specs under `openspec/specs/`. For setup/usage details see [`README.md`](./README.md).

## What it is

`dhis2-app-skeleton` is the EyeSeeTea template for DHIS2 web apps (TypeScript + React). New apps start from it, and it is the `dhis2-react` reference the est-ai agents replicate, so its code is the canonical pattern. It ships a small users/groups/roles example and a CLI script built on the same domain.

## Tech stack

-   **Language**: TypeScript 5.7
-   **Framework(s)**: React 18, DHIS2 (`@dhis2/app-runtime` 3, `@dhis2/ui` 10)
-   **External APIs / clients**: DHIS2 Web API through `d2-api` (imports centralized in `src/types/d2-api.ts`)
-   **Tests**: Vitest 3 + Testing Library (jsdom)
-   **Build**: Vite 7, `d2-manifest`, packaged as a DHIS2 `.zip`
-   **Lint/format**: ESLint 9, Prettier 3
-   **Runtime**: Node v24 (`nvm use`, from `.nvmrc`), Yarn 4 through Corepack (`packageManager` in `package.json`)

## Architecture

Clean Architecture; see [README → Architecture](./README.md#architecture) for the directory layout. Dependencies point inward toward the domain: `src/domain` has no framework or infrastructure dependencies, and all external access goes through repository interfaces.

-   `src/domain/entities/generic/` holds the shared data structures (`Future`, `Collection`, `HashMap`, `Either`, `Struct`, …), see [README → Data structures](./README.md#data-structures-srcdomainentitiesgeneric).
-   `src/CompositionRoot.ts` wires repositories into use cases: `getWebappCompositionRoot` with the `*D2Repository` implementations, `getTestCompositionRoot` with the `*TestRepository` ones.
-   A typical flow: a page or script gets the composition root, calls a use case, and the use case works through the repository interfaces.

## Code conventions

Project rules checked in reviews (extra restrictions, or exceptions to the shared EyeSeeTea rules) live in [`.est_ai/rules/project/`](./.est_ai/rules/project/README.md).

-   New code goes in the correct layer per the architecture above.
-   Import d2-api types and runtime only from `src/types/d2-api.ts`.
-   `src/locales/` is generated by `yarn localize`; translate in `i18n/*.po`, see [README → i18n](./README.md#i18n).

## Verification

Before considering a change done, run the project's checks:

-   **All checks** (`yarn check`): runs every check below, so none is skipped. The `.husky/pre-push` hook runs it too, after the [secrets scan](./README.md#secrets-scan).
-   Typecheck (`yarn typecheck`)
-   Format check (`yarn prettify:check`)
-   Lint (`yarn lint`)
-   Tests (`yarn test`)

## Testing strategy

-   Unit tests cover use cases, repositories, and presentation/command behavior; they live in `__tests__/` next to the code (`*.spec.ts(x)`).
-   Use the in-memory `*TestRepository` implementations (through `getTestCompositionRoot`) to exercise use cases and components without a DHIS2 instance.
-   Shared test setup is in `src/tests/setup.ts`.
-   Add or adjust tests whenever behavior changes.

## Git workflow

-   Format (`yarn prettify`) before committing.
-   Branch from `master` (unless the work depends on an unmerged branch); merge back to the same branch you started from.
-   Branch naming: `feat/<name>` for features, `fix/<name>` for bugs, `refactor/<name>` for refactors, `chore/<name>` for maintenance.
-   Commits follow [Conventional Commits](https://www.conventionalcommits.org/).
